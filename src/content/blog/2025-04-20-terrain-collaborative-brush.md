刚接手地形这块的时候，遇到的第一个大问题不是渲染，是协作。

多个地编会频繁地冲突修改地形。

## 分块只是在降低概率

UE 原本的做法是把地形分块，以降低冲突发生的频率。

但这只是降低概率。任务的需求往往是集中的 —— 这一周所有人都在做同一片区域，对同一个地块的协同修改是必须发生的，不是可以调度掉的。

之前有一个"体外循环"的方案：允许多个地编在各自的客户端上编辑同一个地块，然后由一个服务把这同一个地块导出为各种纹理，进行像素级别的合并和冲突覆盖。

这能解决一部分问题。但它的失败模式很糟：合并算法一旦判断错，出来的不是"某个人的修改丢了"，而是一片谁都没画过的地形。

**合错比冲突更贵。** 冲突至少还看得见，合错要等美术下次打开才发现。

## 画刷

后面在做地形渲染改造的时候，发现了另一条路：画刷。

把每一笔修改，都及时地发送到所有编辑者。类似于"云文档"这样 —— 当你要修改的时候，你看到的就是最新版本。

即使两个人在交替地绘制同一个地方，也不会有冲突了。因为他们甚至可以用画刷"交流"：你看到我在这里抹平，你自然就往旁边去。

这个模型比合并简单，原因有三条：

**传的是操作，不是结果。** 一笔刷子就是位置、半径、强度、通道这几个数，带宽极小，比同步一张高度图便宜几个数量级。

**冲突不是被解决的，是不会产生的。** 所有人都在同一条操作序列上，没有分叉，也就没有需要合并的两个版本。

**人本身就是最好的冲突解决器。** 只要让他们看得见对方在干什么，协商成本远低于任何自动合并算法。

## 同一个思路，我们在配置上也用过

团队上一个项目已经建立了一种"云文档"机制：把在线表格通过 api 抓成 json，直接在 ts 里读。

这件事我更早的时候也做过 —— 做小游戏的时候，我们把配置全部放在 Google Doc 上。当时会选这个方案，是因为在更早的项目里被表格同步折磨得太久了。

Google Doc 算是一步到位，通过 api 把 excel 抓成 json，非常舒适。但后面也发生了两个问题：

- **版本完全没有管理。** 发现了 bug 想找原因，经常已经没法重现了 —— 配置早就被别人改过了。
- **更新策略太激进。** 当时是每一次启动游戏，都通过 api 拉一次最新配置。

这两个问题在现在的云文档上也遇到了，并且由于合作人数众多，甚至还加剧了。

目前所做的两件事：一是可以选择不进行主动更新；二是把云文档的版本和代码版本进行绑定，这样自动更新也不影响正常逻辑。

**同步和版本是两个问题，不能用一个方案糊过去。** 画刷解决的是同步，云文档的版本绑定解决的是可复现 —— 地形那边迟早也要补上后面这半。

## 边界

这套做法后来在一次 Unreal Circle 的分享里讲过，这里补上它不解决的部分：

- 它解决的是"多人同时在线编辑同一地块"。**离线编辑之后的合并，它一点都不解决。**
- 它需要一个常驻服务和在线前提。地编断网的时候，这套东西不工作，断线重连的状态追赶也还没做完。
- 操作序列的持久化和回放还没做完。也就是说，"谁在什么时候改了什么"目前还不能完整追溯 —— 这正是云文档那边已经补上、地形这边还欠着的那一块。
