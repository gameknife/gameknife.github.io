NPC 接大模型的 demo，这两年大家见过不少。NPC 能聊天了，能记住你了，也能即兴发挥了。

问题是很多演示没有回答运行时最普通的几件事：服务断了怎么办，回答慢了怎么办，输出不合法怎么办，几十个人同时想说话怎么办。

我在 gkNextEngine 里做了 AirportSim 和 StudioSim 两个模拟场景，想试一种更保守的放法：让 LLM 参与“接下来想做什么”，但把世界能否继续运转留在普通代码里。

这不是所有游戏 AI 的唯一答案。对需要稳定 tick、可离线运行的模拟游戏，它至少是一条容易控制风险的路。

## 一、先把世界分成两层

AirportSim 的 Layer 0 是确定性的。

值机、安检、排队、登机、航班时刻表，以及旅客状态之间的合法迁移，都由普通状态机负责。LLM 服务完全断掉，旅客仍然会走完主线，只是行为和台词少一点变化。

Layer 1 才交给模型。旅客过完安检以后，是去咖啡店、和身边的人说一句话，还是安静待着；员工遇到事件时，用什么情绪反应。这些允许偶尔无聊、也允许有点意外的部分，适合由模型提议。

代码里 `AirsideIdle` 一类状态就是两层的接缝。Layer 0 决定角色什么时候有资格做选择，Layer 1 只在这个时刻交回一个小结果。

这套分层真正限制的不是模型聪明不聪明，而是它有多大权限。

## 二、DecisionScheduler：先按不可信输入设计

AirportSim 里负责这件事的是 `DecisionScheduler`。

同时只允许一个 LLM 请求在途。异步回调在 worker 线程做解析并把结果入队，主线程 `Tick` 再统一 apply，所以模型回调不会直接碰 Scene 和 agent 状态。

每次 prompt 只给有限感知：当前时间、身份、状态、最近说过的话，以及半径内最多 5 个邻居。能选的动作也会随角色状态缩小。空侧旅客看到的是：

```text
goto / say_to / emote / idle
```

模型被要求只返回一个 JSON 对象：

```json
{
  "action": "goto",
  "target": "咖啡店",
  "say": "来杯咖啡提提神",
  "mood": "happy"
}
```

请求超过 25 个游戏分钟会被丢弃。按默认时间倍率，大约是 10 个真实秒。迟到的回调通过 generation 作废，不会过一会儿又把旧决定写回世界。

服务没启动、服务返回失败、JSON 解析失败或请求超时，调度器会走规则 fallback。预制台词和简单规则不一定有趣，但至少不会因为模型不在线就让机场停摆。

## 三、这次复核也发现：契约还没有变成硬边界

写初稿时，我把上面的 prompt 约束直接写成了“动作白名单、目标合法性和 20 字限制”。重新读当前代码，发现这句话说过头了。

`ParseDecision` 目前做的事情很薄：从回复里找第一个 `{` 和最后一个 `}`，只要 JSON 能解析，就把 `action`、`target`、`say` 和 `mood` 取出来，并标记为 valid。它没有再次检查 action 是否属于白名单，没有验证 target 是否真在当前可达列表，也没有强制截断 20 字台词。

`ApplyResult` 还接受 `use_poi` 这个兼容别名，虽然当前 prompt 不再要求模型输出它。未知 action 可能落进默认分支，错误 target 也可能什么都没发生，但日志仍会记成一次成功的 LLM 决策。

所以现在的安全性主要来自更外层的权限设计：LLM 不直接改航班、队列和主旅程状态，只能调用一小段 apply 逻辑。它缩小了错误的爆炸半径，但不等于验证器已经严密。

这篇发布前我会把“语义无效”单独纳入诊断口径。至于要不要顺手把 parser 变成真正的硬校验，是代码任务，不应该靠宣传稿替它宣布完成。

## 四、诊断面板比一段精彩对话重要

每次决策都会留下一条记录：哪个 agent、游戏内时间、prompt、response、耗时、是否尝试 LLM、最后是成功还是 fallback。UI 里可以看最近 60 条，还有 `decisionsMade` 和 `fallbacksUsed` 两个计数。

这些记录让 prompt 和模型版本有机会被比较。否则看见一段很像人的对话，很容易忘记前面可能已经失败了二十次。

当前日志已经能提供延迟和 fallback 数据，但我还没有跑出一组适合公开的固定样本。因此这里不写“通常一两秒”之类的经验数字。发布前至少固定场景跑 30 次决策，记录中位数、P95、fallback 率和语义无效率，再决定本地模型是否真的够用。

可观测性不是给文章添一张 profiler 图。它是这个系统能不能继续调下去的前提。

## 五、本地模型和串行预算

`gnb llm` 会拉起 llama.cpp，暴露 OpenAI 兼容接口。当前 active 配置是 `gemma-4-E4B-it-Q4_K_M`，编辑器、ScadStudio 和游戏可以复用同一个本地 server。

我选择本地小模型，不是因为已经证明它“绰绰有余”，而是 Layer 1 的任务被刻意切小了：从少量动作里做选择，再生成一句短台词。这个问题是否真的适合当前量化模型，仍然要看上面的实测分布。

同时只有一个请求在途，能保证并发成本有上限，也让线程模型简单。它不能自动证明吞吐量足够，更不能保证一个排队很久的决策到达时仍然新鲜。

当前调度器用冷却时间、轮询游标和事件优先控制机会分配。场景规模增大以后，还需要继续观察队列等待、决策到达时的状态变化，以及高优先事件会不会长期挤掉普通角色。这些问题不能用“一次请求只要几秒”一笔带过。

## 六、和 SCAD 篇相似，但不完全一样

上一篇的 SCAD 管线也是让概率系统提出结构化文本，再由确定性程序解析和执行。两边确实有共同思路：模型负责语义变化，普通代码负责资源和状态边界。

但 SCAD 的输入更接近一次性编译，失败以后可以停下来修；游戏运行时一直在走，旧结果还会过期，错误动作也可能影响别的角色。因此运行时调度多了超时、主线程 apply、冷却、事件优先和 fallback，不能只靠一个 JSON schema 就复制上一套结论。

我现在能给出的窄结论是：确定性骨架可以降低模型错误的影响，也能保证服务离线时世界继续运行。它不能保证“永远正确”，因为状态机、fallback 和 apply 代码本身同样会有 bug。

## 写到这里

AirportSim 当前可以这样启动：

```bash
./gnb llm setup
./gnb llm serve
./gnb run AirportSim
```

不起模型也能运行，角色会走规则路径。这不是降级失败，而是 Layer 0 应该兑现的最低行为。

AI 这几篇到这里先收住。接下来回到渲染主线，继续写那些只有把一条 Vulkan 路径真的跑起来以后，才会暴露出来的工程问题。
