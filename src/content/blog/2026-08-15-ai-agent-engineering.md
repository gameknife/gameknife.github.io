先说明一下：这篇文章讨论的是我怎么和 AI 一起写引擎。初稿本身也是 AI 根据仓库、commit 和开发文档整理出来，再由我修订。这个过程还挺符合主题的。

大部分时候，我仍然是一个人在业余时间写 gkNextEngine。

白天上班，处理完家里的事情，晚上再坐到电脑前。这个时间预算和以前没有本质区别，一天多不出几个小时，精力甚至比十几年前写 gkEngine 的时候差了不少。

但进入 2026 年之后，项目的开发速度完全变了。

这一代模型配合 Codex、Claude Code 这类 code agent，已经不只是帮我补几行代码。它们可以读仓库、查调用链、改几十个文件、构建、跑测试、看截图、根据错误继续修，最后把过程和风险交回来。

截至 2026 年 7 月 15 日，从 `2026-01-01 00:00 +08:00` 起算，这个仓库有 609 次提交（含 merge commit）、144 个活跃开发日。按仓库自己的 `gnb loc` 口径，`src/` 下有 776 个第一方文件、142,652 行代码，不含 ThirdParty；里面包括 31,084 行的 Engine core、16 个可选模块、编辑器、工具、测试，以及 12 个游戏子项目。

它当然不能和 UE 这种工业巨兽比。但这也早就不是一个几千行的 renderer sample 了。Vulkan、C++20、Slang、路径追踪、GPU-driven、ECS、反射、QuickJS、物理、五个平台、十几个程序，每一项都能制造真实的工程问题。

如果只看一部分边界清楚的代码研发和迭代任务，我现在一个人加上一组 AI agent，确实能达到以前小团队才有的吞吐量。有些阶段甚至更快。至于代码风格、模块边界和文档一致性，则不是模型自动送的，后面会讲我是怎么守住的。

这不是因为 AI 突然学会了"一键生成游戏引擎"。

恰恰相反，我这半年最深的体会是：模型能力只决定上限，工程环境决定你能不能碰到这个上限。

这篇想把这件事讲清楚。

## 一、真正的变化，不是代码写得更快了

我很早就在用 AI 辅助编码。

最初是补全。写一个函数名，它猜后面十几行；写一段注释，它帮你填实现。这个阶段当然有用，但本质上还是一个更聪明的输入法。工作的拆解、上下文的组织、错误的定位和最后的验收，全都在我脑子里。

Code agent 不太一样。

现在我可以交给它一个完整任务：先读现状，找出依赖，写一份计划，然后动代码；改完只构建受影响的 target，跑对应测试；如果是渲染或 UI，再启动隐藏窗口跑到稳定帧，截一张图回来。

也就是说，AI 不再只压缩"打字"这一段时间。它开始接管一整段可以闭环的研发循环。

以前我一晚上只有一条思考链：写代码，等编译，调试，再写。任何一步卡住，这两个小时就没有了。

现在我可以把边界清楚的工作拆开。一个 agent 调研 Vulkan 行为，一个整理调用面，一个实现独立模块，我自己同时看架构和最终效果。它们不是简单地把同一双手变快，而是增加了同时运转的思考回路。

我觉得这才是从 Copilot 式辅助，到 agentic coding 的分界线。

当然，agent 也不是越多越好。研究任务、独立 Demo、互不相交的工具模块很适合并行；动 Engine 公共头文件、CMake 装配和 GPUScene 这类中心结构时，并行修改反而很容易互相踩。我现在更倾向于并行调研，串行收口；外围可以铺开，核心一次只允许一个明确方向。

它看起来已经有点像带团队，只不过组织成本换了一种形态。

6 月 10 日那天的 git log 很像这种工作方式的切片。16:32 提交重构基线；16:51 一边出现 ImGui 1.92 兼容修复，一边完成 Phase 1；17:07 到 17:12 连续落下 Phase 2 和删语音输入；20:12 到 21:21 又完成 AI / Remote、编辑器 UI 和 god class 的几轮拆分；22:52 还有一笔 AirportSim 改进。

这些时间只能证明 commit 的交付顺序，不等于我连续敲了六个小时，也不能精确还原每个 agent 同时在做什么。但它至少比“效率提升了很多”具体：同一天里，重构、兼容修复和 Demo 迭代确实在交错推进，我负责判断每一批结果能不能留下。

## 二、游戏引擎对 AI 并不友好

说实话，游戏引擎可能是最不适合拿来展示"一句话生成应用"的项目之一。

大型 C++ 工程的错误经常不在当前文件。一个 buffer 生命周期改错，可能在几十帧以后变成 driver crash；一个头文件多 include 了东西，可能只在 non-unity build 或 iOS 上暴露；一段 shader 在 NVIDIA 上正常，到 AMD 或 MoltenVK 上才开始花屏。

更麻烦的是，编译通过不代表正确。

一个 Web 表单只要能打开、能提交，功能大致就能判断。渲染器即使输出了一张图，也可能法线错了、历史帧串了、阴影漏了、材质只是"看起来差不多"。这些问题没有审美和图形经验，很难只靠日志发现。

LLM 又特别擅长写"看起来应该对"的代码。

它能很快给你一段 Vulkan barrier，一段 CMake，一套异步回调。大部分时候语法都对，API 名也对。但这三段东西是不是符合你这个引擎的资源所有权、线程模型和平台边界，是另一回事。

所以我很早就放弃了一个幻想：让模型完整理解整个引擎，然后替我做所有决定。

更实际的做法，是让仓库本身给它提供足够清楚的局部世界。每个任务只需要理解一个可控范围，每一步都有可以执行的验证，失败以后也知道怎么退回来。

换句话说，与其继续期待上下文窗口无限变大，不如先把工程改造成不需要每次都读完整个世界。

## 三、先给 AI 修一条能工作的路

这半年我做了不少看起来"不直接出 feature"的事情：整理 `AGENTS.md`，写分层文档，统一构建命令，补 targeted build，做隐藏窗口截图，给游戏增加状态查询和自动断言。

这些东西对人有用，对 agent 更有用。

### 1. 仓库要能被读懂

gkNextEngine 有一份统一的 `AGENTS.md`。里面不讲宏大愿景，主要讲具体规则：命名怎么写，哪个目录不能动，改 Engine 要构建哪两个 target，改一个游戏只需要构建谁，渲染改动怎么截图，什么时候才值得全量重编。

复杂任务会再有一份 plan 或 spec。现状基线、目标边界、明确不做什么、每个阶段的验收标准，全都写进去。

以前技术文档的读者默认是"未来的我"或者其他开发者。现在又多了一类读者：下一轮接手任务的 agent。

这会反过来逼着文档更具体。诸如"适当重构一下""注意兼容性"这种话，人看了都不一定知道怎么做，AI 看了只会自由发挥。真正有用的是："核心不得反向依赖模块""这个阶段只移动文件，不改变行为""完成后构建 A 和 B，再用场景 C 截图"。

### 2. 环境要能一条命令跑起来

我后来写了一个 Go 工具叫 `gnb`，把五个平台的 setup、build、run、test、资源包、dashboard 和本地 LLM 全部收进去。

对人来说，这是少记几条 CMake 命令。对 agent 来说，它把环境复杂度压成了稳定接口。

Agent 不需要研究我的 Vulkan SDK 放在哪、vcpkg 怎么 bootstrap、哪个程序需要哪些模块。它只需要知道：

```bash
./gnb build gkNextRenderer gkNextUnitTests
./gnb shot --scene assets/models/playground.glb
./gnb validate --script assets/agentscripts/smoke.agentscript.json
```

能被 agent 开发的项目，首先得是一个 agent 真能在本机跑起来的项目。

### 3. 结果要能被验证

这是最重要的一层。

`gnb shot` 会用隐藏窗口启动真实 Vulkan swapchain，渲染到稳定帧，截图，然后自动退出。`gnb validate` 更进一步，可以用声明式 JSON 模拟键盘、鼠标、点击和拖拽，等待游戏状态，查询 `engine.*`、`scene.*`、`cvar.*` 或游戏自己的状态，做断言，最后写 JSON report，并用退出码表示成功或失败。

过去 agent 改完渲染代码，只能告诉我"编译通过"。现在它至少有机会把场景真的跑起来，看一眼输出；交互功能也不必靠临时在游戏里塞自动分支来验证。

### 4. 失败以后要能退回来

可恢复不是一个“撤销 AI”按钮。我的做法比较朴素：复杂工作按 Phase 拆，小步提交；每一阶段记录改了什么、跑了什么验证，agent worktree 和主工作区分开。某个方向错了，可以丢掉那一阶段，也可以只回退一笔边界清楚的 commit。

这套办法不能消灭错误，但能限制一次错误扩散多远。对会同时改几十个文件的 agent 来说，这一点和自动测试同样重要。

我现在越来越觉得，所谓 AI Native 代码库，至少应该满足四件事：可发现、可执行、可验证、可恢复。

接一个聊天面板，反而是最不重要的那一件。

## 四、人和 Agent 到底怎么分工

我没有把自己变成一个只会写 prompt 的产品经理。

实际开发里，我仍然会直接读代码、下断点、看 RenderDoc、手改结构。有些最近的 commit 就直接叫 `hand refactor`，这倒是很诚实。AI 卡在错误方向里时，继续追加十轮 prompt 通常不如自己改掉关键的三十行。

但我的工作重心确实变了。

我现在主要负责五件事：决定做什么，决定不做什么，划模块边界，判断画面和手感，最后为合入结果负责。

Agent 更适合做这些：盘点调用面，把计划拆成阶段，执行大量机械改动，补测试和文档，处理编译错误，以及把同一套修改传播到多个平台和调用点。

这和带一个工程团队其实很像。区别是 AI 不会因为机械工作太多而烦，也不会介意我把同一件事推倒重来；但它也不会真正替我承担判断错误的后果。

所以我不太认同"以后不需要懂代码，只要会描述需求"这种说法。

至少在引擎开发里，AI 把技术判断的杠杆放大了。判断对，几十个文件一起往正确方向走；判断错，它也能用很高的质量把错误架构铺满整个仓库。

## 五、四件实际发生的事

这套方法不是理论。下面四件事都发生在这个仓库里，commit 都在。每一件展开都是一篇文章的量，这里只给结果，细节接下来几周单独成文。

第一件：AI 把 Engine core 砍掉了两万多行。今年 6 月 `src/Engine` 涨到 55,279 行，我和 AI 写了一份目标读者是 agent 的重构 runbook，agent 分 Phase 执行，每个 Phase 的行数写进 commit message。第一轮降到 33,924 行；截至 7 月 15 日，core 是 31,084 行，旁边有 16 个按 target 装配的模块。这里大部分是从核心外移，不是让仓库总量凭空消失。实录下一篇讲，包括它翻车的地方。

第二件：Demo 不再是舍不得做的消耗品。以前个人写引擎，做一个完整 Demo 的机会成本太高，于是很多个人引擎只有几个漂亮场景，能不能做游戏从没被验证过。AI 把原型成本压下来之后，我反过来用 Demo 测引擎——现在仓库里有 12 个游戏子项目：MagicaLego、BrickPlayer、Brotato3D、KongLie3D、CharacterDemo、Flappy（C++ / TypeScript 双版本互为校验）、Voyage3D、AirportSim、StudioSim、NextRA、CitySolSim 和 TruckerDemo。它们不是换皮场景，每一个都在逼引擎回答真实问题：输入怎么统一、脚本生命周期怎么和 C++ 对齐、UI 怎么和 bindless 渲染共存、场景重载以后谁还持有旧指针。以前这些问题要等一个"真正的游戏项目"来暴露，现在可以先用一个小项目把争论变成运行结果。

第三件：让 LLM 写可执行的 3D 语言，而不是直接吐模型。从 MagicaLego 的 mlscript，到 ScadStudio 的对话式 OpenSCAD 建模，再到用 SCAD 描述角色骨骼和动画的 ScadRig。核心想法一句话：给模型一个约束足够强的中间表达，不要让它直接跨过所有工程中间层。单独成文。

第四件：把本地 LLM 放进游戏运行时，但不让它掌管世界规律。AirportSim 和 StudioSim 都是两层结构：Layer 0 是确定性状态机，LLM 完全断掉世界照常运转；Layer 1 才交给模型，决定一个旅客候机的四十分钟是喝咖啡还是逛书店。当前实现会要求 JSON 契约、解析结构并在服务失败或超时时走 fallback；这次复核也发现，动作白名单和目标合法性还没有在 parser 层做成真正的硬约束。确定性层限制了模型权限，但验证器本身还有债。单独成文。

## 六、代码质量为什么没有一起失控

这里必须说一句不太讨喜的话：AI 不会自动带来高质量代码。

它只会自动带来更多代码。

gkNextEngine 目前还能保持比较一致，主要不是因为某个模型特别有洁癖，而是仓库里有几层硬约束。

第一，依赖方向尽量单向。Application 可以依赖 Modules，Modules 可以依赖 Engine，Engine 不能反过来知道具体游戏和领域模块。Agent 判断不清楚时，至少有一条物理边界挡着。

第二，优先使用主流第三方库。SDL、glm、entt、Jolt、QuickJS、Slang、tinygltf、meshoptimizer，这些东西模型本来就认识。自己再包三层独家 RHI，不但人要重新学，AI 也只能在仓库里猜。

第三，每次修改都有和风险相称的验证。普通模块做 targeted build，核心改动带 unit tests，渲染改动要截图，交互流程走脚本断言，大重构才跑全量构建。验证成本必须足够低，否则 agent 和人都会开始偷懒。

第四，文档和代码一起改。下一轮 agent 读到的是当前架构，而不是半年前的幻觉。做不到这一点时，旧文档甚至比没有文档更危险。

第五，持续重构。AI 写出的第一个版本经常只是"能工作"。我会让另一轮 agent review，也会自己手工收口。重复逻辑、god class、反向依赖一旦开始形成，就尽快处理，不等它长成历史包袱。

所以，代码的一致性不是模型给的，是反馈回路给的。

模型越强，这套回路越重要。因为它犯错以后，扩散得也更快。

## 七、真话时间：这套方式也挺累

"一个人顶一个团队"听起来很轻松，真实感受并不是。

以前累在写。现在更多时候累在连续做判断。

几个 agent 同时回来，每个都给你一份看起来合理的方案；一个说应该抽象接口，一个说应该直接搬模块，一个说当前架构已经够好。你得快速读懂它们，判断谁漏了平台，谁把问题想复杂了，谁虽然编过但其实破坏了原来的设计。

Review 会成为新的瓶颈。

模型也很容易讨好当前任务。你让它实现功能，它通常会努力把功能塞进去，而不是提醒你“这个东西也许根本不该做”。核心重构后就发生过一次很实在的问题：AgentDriver 的文件还在，装配关系却丢了，编译和单测都没有发现，直到端到端功能真正用起来才暴露。局部验收给窄了，AI 会非常高效地交出一个“在验收范围内正确”的结果。

上下文也会腐烂。这个项目迭代太快，六月写的“当前有 7 个 Demo、6 个模块”，到 7 月 15 日已经变成 12 个和 16 个。文档、宣传稿、README、代码注释都可能落后。维护这些上下文本身，已经成了正式开发工作。

还有一些问题 AI 暂时替代不了真实设备。Windows 上通过，不代表 macOS 的 Vulkan-on-Metal 没事；NVIDIA 画面对，不代表 AMD 驱动接受；Android 和 iOS 的构建错误，有时就是要在那台机器上慢慢磨。

最后，AI 会显著增加"可以做什么"，但不会增加我晚上的时间。

以前 backlog 很长，是因为做不完。现在 backlog 更长，是因为突然有太多东西看起来都做得完。决定不做什么，比实现本身更难了。

## 八、我目前得到的几个结论

第一，AI Native 不是在产品里接一个聊天框，而是让整个工程对 agent 友好。

它应该有清楚的地图、稳定的工具、短的反馈回路和失败后的退路。模型换一代，这些基础设施仍然有用。

第二，代码库越小，AI 的收益越大。

不是说 142,652 行很小，而是核心认知面必须小。全部功能可以增长，但每个任务需要理解的闭包应该受控。把 Engine core 保持在 3 万行附近，并不是洁癖，是在给人和模型共同保留认知带宽。

第三，结构化中间表达会重新变得重要。

SCAD、mlscript、反射元数据、agent validation script，本质上都是人、LLM 和引擎之间的协议。AI 最适合在语义和结构之间做翻译，而不是直接绕过工程系统生成最终状态。

第四，运行时 Agent 最好建立在确定性骨架之上。

物理、经济、任务流、资源所有权这些东西，还是应该由普通程序保证。LLM 适合负责选择、对话、解释和变化。这样它在线时世界更有趣，离线时世界也不会坏。

第五，一个人的上限确实被抬高了。

这不等于团队没有价值。美术、设计、制作、用户研究、商业判断，并不会因为 code agent 出现就自动消失。更准确的说法是：以前必须先组一个团队才能验证的技术系统，现在个人也有机会先把它做到足够完整。

最小可行团队的尺寸，正在发生变化。

## 写到这里

2024 年我重启这个项目，最初只是想补一补现代渲染的课。

到了 2026 年，问题已经从"一个人能不能写完这些东西"，慢慢变成了"当代码生产不再是最大瓶颈，我怎么保证项目还在往一个方向长"。

这个变化挺大。

AI 没有替我决定 gkNextEngine 应该是什么。它只是让每一个决定的结果来得更快：正确的架构更快变成系统，错误的想法也更快变成技术债。

所以最后留下来的工作，还是判断、取舍和审美。
