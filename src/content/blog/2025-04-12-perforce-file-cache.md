开发的前两年，p4 服务器一切都十分正常。

最近开始出现一个现象：每次创建完分支后，会遭遇全公司的大堵车。

## 症状

时间点非常规律，一开始是每周四上午。

我们每周四有一个例行的周版本分支要 branch 出来。branch 之后，所有人的 sync 都会卡住。有几次 p4 服务器的内存资源被耗尽了，进程列表里全是拥塞的 p4d。

第一轮判断是服务器规格不够。做了几次调整，也分析出需要换一台专业服务器来提供 p4 服务。

然后就撞上了本周这次更严重、也更诡异的拥塞。

## 结论和我们最初的猜测不一样

几个人重新分析了一圈，慢慢得出了这个结论：

- 如果只依赖磁盘 IO，p4 服务器是绝对扛不住超过三四个人的大量 sync 同步的；
- 之前一直没问题，是因为 Linux server 的 file cache 一直在命中；
- 而 branch 分支（包括这周做的一些维护操作），刚好把这个 file cache 清空了。

也就是说，这台服务器两年来的"正常"，一直建立在一个我们没有意识到的前提上。

**负载没变。变的是缓存命中率。**

至于 branch 为什么会冲掉 cache，这一点我标为推断：branch 要写入大量 integration record，同时会碰到大量 db 和 archive 文件，热数据被挤出 page cache。我没有做前后的 page cache 采样来证实这条。

## 官方文档里早就在讨论

顺着这个方向查下去，发现有大量 p4 文档在讨论这件事。

在 Linux 服务器上，官方的建议是给系统留下相当比例的内存来 cache IO —— 我当时看到的说法是 60% 左右。具体数字请以你手上那个版本的文档为准，不同版本的表述不完全一致。

这句话翻译过来是：**p4d 自己占多少内存，不是唯一要考虑的事。你还得给它下面的文件系统留够。**

一台内存看起来"很够"的服务器，如果 p4d 把大部分吃掉了，剩下的 page cache 撑不住热数据，磁盘就会直接暴露在几十个人的 sync 面前。

## 所以这篇没有"修好了"的结论

最终方案周末已经在实施，还在观察。

我能拿出来的只有一个方法上的收获：**一个跑了两年都正常的系统突然出问题，先别急着问"哪里坏了"，先问"什么变了"。**

这次变的东西根本不在监控上。我们监控了 CPU、内存和磁盘 IO，唯独没有监控缓存命中率 —— 而它才是那两年正常的真正原因。

## 还没验证的

- 换专业服务器之后的效果，还没有数据；
- 我们没有做 A/B。"file cache 是主因"目前只是最能解释现象的那个解释，不是被证明的那个；
- branch 操作本身能不能优化到不冲 cache，还没查。
