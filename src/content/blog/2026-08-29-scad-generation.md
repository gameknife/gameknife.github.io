AI 生成 3D 内容，现在有很多路线：直接生成 mesh 或体素，也有 NeRF、Gaussian Splatting 这类更接近场景或视图表示的方案。它们解决的问题并不完全相同。

我这里关心的是另一件事：怎么生成一个需要进入工程、能继续编辑的资产。绕了一圈之后，我越来越偏向一种看起来很古典的办法：让它写代码。

这一篇讲这条路在 gkNextEngine 里是怎么一步步走出来的——从乐高指令，到对话式 OpenSCAD 建模，再到用 SCAD 描述一个会走路的角色。

---

## 一、起点：MagicaLego 的 mlscript

最早的尝试很小。

MagicaLego 是我的赛博乐高子项目。想让 LLM 帮玩家搭东西的时候，我没有让它直接操作游戏内存，而是给它定义了一套很小的指令语言 mlscript：`place`、`move`、`turn`、`repeat` 这些命令。

模型生成脚本，脚本先解析、校验，再由游戏执行。

这个设计当时更多是出于安全考虑——不想让模型输出直接碰运行时状态。但它意外揭示了一个更重要的事实：模型写这种结构化指令的正确率，远高于让它直接输出坐标列表。

道理想通了也简单。LLM 的训练数据里包含大量代码和结构化文本，“生成一段有语法、有重复结构的指令”通常比直接维持一大组精确坐标关系更接近它的长处。

问题是 mlscript 的词汇量太小，只够搭积木。想描述任意几何，需要一门真正的 3D 语言。

---

## 二、为什么是 OpenSCAD

这门语言不用发明，现成的：OpenSCAD。

程序员圈子里它小有名气——用代码描述实体几何，cube、sphere、cylinder 加上 CSG 布尔运算，参数改一下模型跟着变。3D 打印社区用了十几年。

对我来说，它适合这条管线主要有三个原因。

第一，公开代码里有不少 `.scad` 示例，主流模型通常认识基本语法，不必只靠我的仓库临时学习。这和引擎选第三方库是同一个逻辑：优先采用已有资料和工具生态的表达，模型更容易给出可用起点。

第二，它天生是参数化的。"把杯子加高一点"这种修改，对 mesh 是重新生成，对 SCAD 只是改一个数字。

第三，它是文本。可以 diff、可以进版本管理、可以局部修改、可以写测试。

于是 ScadStudio 的形态就出来了：用户用自然语言描述模型，LLM 生成 OpenSCAD 源码，引擎解析并实时渲染。

---

## 三、代价：引擎得自己长出一套 SCAD 工具链

这条路不魔法的地方在于，引擎这边要付出实现。LLM 写出来的 SCAD，总得有东西把它变成三角形。

gkNextEngine 里这套东西现在长这样：自己的 lexer、递归下降 parser、AST evaluator，CSG 布尔交给 Manifold（真布尔，不是 hack），text() 字形走 FreeType（中文都能刻），凹多边形和带洞轮廓用 earcut 三角化。整个数据流是：

```
.scad → Lexer → Parser → AST → Evaluator
   → 图元变三角汤，CSG 节点走 Manifold，2D 轮廓走拉伸
   → 按 module 调用树重建场景层级 → 上传 GPU，实时显示
```

支持的子集也不是玩具级：module / function 定义、for / if / let、list comprehension、`linear_extrude` / `rotate_extrude`、`hull`、`$fn`，以及 `children()` 这类进阶语义。仓库里两个验证场景，一个是古城（城墙、城门、房屋、挂着"酒楼"二字的招牌），一个是啤酒杯（rotate_extrude 的把手、sphere 堆的泡沫、半透明玻璃材质），都是零 warning 加载。

截至 2026 年 7 月 15 日，`ScadLoader` 按 `gnb loc` 口径是 26 个文件、5,074 行，后来在核心层重构时整体拆成了独立模块。它是这条技术路线里最贵的一笔投入，但它买到的东西值：在同一版本的可执行程序、同一设置和同一平台上，同一段 SCAD 会沿同一条求值路径得到稳定结果。

概率的部分收在模型那一侧，工程这一侧全是确定的。

## 四、修复回路：错误是资产，不是失败

生成的 SCAD 当然会出错。语法错、几何自交、布尔运算退化，都会发生。

关键在于：其中一部分错误可以被结构化反馈。语法错误通常能定位到 token 和行号；求值或 CSG 失败则复杂一些，有时能指出 module，有时只留下 warning 或空结果，还需要结合视口判断。

把这些信息连同源码喂回模型，它就有机会局部修改。早期对话记录没有完整保存，所以我不会声称它“通常一两轮收敛”；发布这篇之前，应该重新录一段从失败到修复的真实过程。

直接生成 mesh 也不是完全不能修。视觉反馈、法线检查和几何度量同样可以驱动修复。SCAD 的区别是源码保留了参数和模块边界，“杯把太细”可以落到一个局部表达式上，diff 也能说明到底改了什么。

生成 → 校验 → 报错 → 修复，这个回路能转起来，靠的就是中间表达有结构。这其实就是程序员和编译器的关系——LLM 在这个回路里扮演的角色不是神笔马良，是一个会看报错的程序员。

## 五、再往前一步：用 SCAD 描述会动的角色

场景和静物走通之后，我把这条路又推了一步：角色。

ScadRig 是一套刚体骨骼角色方案，语义和 Minecraft 那类方块人一致——刚体部件挂在骨骼层级上，不做蒙皮。它的资产格式就是一个合法的 .scad 文件：

```scad
module bone_torso() {
    color(ROLECOLOR) cube(...);              // 骨骼体内的几何，刚性绑定
    translate([0,0,0.54]) bone_head();       // 调用点的变换 = 子骨骼 pivot
}
module bone_root() { translate([0,0,0.84]) bone_torso(); }
bone_root();

anim_walk = [                                 // 动画 clip 是纯数据
    ["bone_leg_l", "rot", [[0,[35,0,0]], [0.4,[-35,0,0]], [0.8,[35,0,0]]]],
];
```

约定很少：`bone_` 前缀的 module 是骨骼，骨骼调用点外层的 translate / rotate 就是绑定姿态，顶层 `anim_*` 变量就是关键帧动画。违反约定只 warning，不失败。

这个格式有个我很喜欢的性质：它同时是三种东西。对引擎，它是运行时资产，加载后由动画器采样驱动；对人，它是普通 SCAD 文件，原版 OpenSCAD 打开就能看到绑定姿态；对 LLM，它是可以生成、可以增量修改的代码——"让走路动作摆臂大一点"就是改两个关键帧数字。

仓库里第一个角色 agent_basic.scad，7 根骨骼、约 250 个三角形、idle / walk / sit / work 四个动作，现在在 AirportSim 里当旅客和员工。机场、古城、办公室这些场景，也都保留为人和 AI 都能读、能改、能 diff 的文本。

## 六、这条路的边界

技术诚实一下，这条路不是万能的。

它擅长的是结构化的东西：建筑、道具、家具、机械、方块角色。CSG 的表达力天花板摆在那里，你不会用它建一张真实感人脸，也不会用它做一棵形态自然的树。那些领域，直接生成的路线（以及传统的美术管线）仍然是对的。

生成质量也依赖模型的空间推理，复杂空间关系它仍然会犯错，只是错了能修——这是和吐 mesh 路线的本质区别：不是不犯错，是错误可收敛。

所以我的结论不是“所有 3D 生成都该写代码”，也不是直接 mesh、NeRF 或 Gaussian Splatting 走错了路。更窄的结论是：当内容需要版本管理、局部修改、参数化，并且要继续被工程系统消费时，结构化中间表达很值得优先尝试。

LLM 负责把模糊意图翻译成结构化表达；引擎负责确定性执行、校验和渲染。资产不是一个来历不明的二进制 blob，而是一段可以审的程序。
