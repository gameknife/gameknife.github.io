我对 Python 是有成见的，而且很具体：

- 解释语言，性能垃圾；
- 依赖缩进，语法松垮，不严谨；
- 看不懂，难受。

第三条最诚实。

## 第一次松动：写 Blender 插件

之前写 Blender 插件的时候，已经体会过 Python 的便利。

它毕竟是一门使用者极多的语言，也是很多大厂的固定语言（对比一下 Lua 的处境）。它的语法分析工具已经非常强大，写插件时的开发环境相当舒适 —— 和我一直青睐的 TypeScript 可以说不相上下。

但那次之后我的结论只松动了一半：开发体验是好，性能上一定还是有问题的。

## 第二次：那批批量转换

这次做一批游戏资产的批量转换工具链。这个领域里前人的工作大量落在 Python 上，我只能又捡起来。

中间遇到一些数学运算，copilot 提醒我可以用 numpy 和 scipy。

深入看了一下才发现：**这些库背后都是原生代码在跑**，甚至算法本身也经过顶尖工程师的高度优化。

这一下才算茅塞顿开。

我一直在跟一层薄薄的外壳较劲。真正干重活的那部分从来不是 Python 写的，Python 只是那个把它们串起来的语言 —— 而"把东西串起来"恰好是它最擅长的事。

一门语言的性能，不完全等于它自己的执行速度；也取决于它能多顺手地调用到别人写好的快代码。这一点我认得太晚了。

## 顺手证实的第二件事：进程池

同一批工作里还有一个收获。

Python 的 Process Pool 非常好用，进程之间要共享数据可以走 Manager。

那批转换任务，单进程跑下来要一个多小时。改成 Pool 起 24 个进程，在 3900X 上不到 10 分钟就跑完了。

对我来说这里有个观念上的转折：以前遇到"太慢"，第一反应是换语言、写 C++。但这类任务是天然可并行的 —— 每个资产之间毫无关系。先把它铺满核心，比重写一遍便宜得多，也快得多。

## 顺带记一个坑

同一批工作里的另一条经验，和 Python 无关，但值得写下来：

**UE 的编辑器模式做批量 FBX 导入不靠谱，走 `UnrealEditor-Cmd` 靠谱得多。**

编辑器模式下崩了好几次，原因基本都指向 GPU query 和显存不足。有一次显卡直接掉了，机器都拉不起来（AMD RX 6600XT）。

批处理就该走无头的那条路 —— 它不需要渲染，也就不该为渲染的那部分资源买单。
